## Context

Дашборд собирается из независимых React-виджетов, использующих TanStack Query. Сейчас 14 виджетов показывают текст «Загрузка...», причём 13 из них до получения данных возвращают элемент вне своей обычной карточки. Ещё несколько условных виджетов возвращают `null`, пока данные отсутствуют. В результате загрузка меняет ширину и высоту колонок, особенно при первом открытии страницы и выборе периода, для которого ещё нет кэша.

Размеры содержимого различаются: компактные `CardAmount`, графики с заранее известной областью, таблицы и списки с неизвестным количеством строк. Полностью исключить изменение высоты динамических списков без фиксированных прокручиваемых областей невозможно, поэтому дизайн ориентирован на устранение схлопывания карточек и уменьшение, а не формальную гарантию нулевого CLS для произвольного количества записей.

## Goals / Non-Goals

**Goals:**

- Заменить видимый текст первичной загрузки на согласованные skeleton-состояния.
- Сохранять оболочку и характерные размеры каждого виджета во время загрузки.
- Разделить первичную загрузку без данных и фоновое обновление уже показанных данных.
- Переиспользовать единый визуальный примитив без переноса предметной структуры виджетов в `shared`.
- Обеспечить доступную семантику и безопасную анимацию с учётом reduced motion.

**Non-Goals:**

- Переработка сетки дашборда или введение фиксированной прокрутки для всех динамических списков.
- Изменение API, query keys, правил кэширования или глобального `staleTime`.
- Создание новых error-state компонентов и пересмотр обработки ошибок запросов.
- Добавление skeleton-состояний в формы, диалоги и mutation-кнопки за пределами виджетов дашборда.

## Decisions

### 1. Skeleton вместо центрального спиннера

Первичная загрузка будет отображать skeleton, повторяющий крупные блоки будущего содержимого. На дашборде одновременно загружается много независимых областей; набор спиннеров не передаёт будущую геометрию и оставляет проблему layout shift. Спиннеры остаются уместны для компактных действий, но не являются основным состоянием виджетов.

### 2. Общий визуальный примитив, специализированные композиции у владельцев разметки

В `src/shared/ui/skeleton/` появится базовый прямоугольный `Skeleton`, принимающий обычные свойства элемента и `className`. Он отвечает только за фон, скругление и анимацию.

Композиция, повторяющая `CardAmount`, будет находиться рядом с `CardAmount`, поскольку этому компоненту принадлежат его размеры. Skeleton-разметка графиков, таблиц и списков останется в соответствующих виджетах либо в небольших нейтральных вспомогательных компонентах, если во время реализации обнаружится точное повторение. Это сохраняет направление зависимостей Feature-Sliced Design и не помещает знания о финансовых виджетах в универсальный примитив.

Альтернатива — один `WidgetSkeleton` с множеством вариантов — отклонена: он быстро станет связан с конкретной раскладкой страницы и усложнит независимое изменение виджетов.

### 3. Сохранять реальную оболочку карточки

Loading-ветка каждого виджета должна рендерить те же внешние классы ширины, `min-width`, высоты и `Card.Base`, что и загруженное состояние. Известные заголовки можно показывать сразу; skeleton заменяет только данные и визуализацию.

- Компактные карточки сумм используют skeleton, совпадающий с закрытым состоянием `CardAmount`.
- Графики резервируют существующую область `Chart.Root` и её ширину.
- Таблицы и прогресс-списки показывают несколько строк-заглушек и используют общую минимальную высоту для loading и loaded состояний.
- Условные виджеты после успешного пустого ответа сохраняют карточку и показывают empty state, а не удаляют весь элемент из сетки.

Для списков с неизвестным количеством строк skeleton не пытается предсказать окончательную высоту. Он предотвращает схлопывание до одной строки; дальнейший рост при большом наборе данных считается допустимым компромиссом.

### 4. Первичная загрузка и refetch имеют разное поведение

Skeleton показывается только когда у обязательного запроса ещё нет пригодных данных. Если TanStack Query выполняет refetch при наличии данных, текущий контент остаётся на экране. При переключении на новый период без кэша показывается skeleton нового состояния.

`keepPreviousData` не включается глобально: показ значений предыдущего месяца или года под уже изменившимся селектором может восприниматься как актуальный результат. При необходимости индикатор фонового обновления можно добавить позднее, но он не должен заменять содержимое.

### 5. Единая доступная семантика

Контейнер загружаемого виджета получает `aria-busy="true"`, а одна скрытая подпись сообщает «Загрузка». Декоративные skeleton-блоки скрываются от accessibility tree, чтобы screen reader не озвучивал каждую полоску. Анимация отключается через `motion-reduce`/`prefers-reduced-motion`.

## Risks / Trade-offs

- [Skeleton не совпадёт с фактическим числом строк] → Использовать минимальную репрезентативную высоту и не обещать отсутствие роста для динамических коллекций.
- [Много одновременно анимирующихся блоков увеличат нагрузку] → Применять лёгкую CSS-анимацию без JavaScript и отключать её при reduced motion.
- [Минимальная высота добавит пустое пространство в empty state] → Подбирать размеры по существующим карточкам и центрировать понятное сообщение об отсутствии данных.
- [Разрозненные локальные композиции приведут к дублированию] → Выносить общий компонент только после выявления одинаковой геометрии как минимум у нескольких виджетов.

## Migration Plan

1. Добавить и экспортировать базовый `Skeleton`.
2. Добавить skeleton-композицию для `CardAmount`.
3. Последовательно перевести компактные, графические и табличные виджеты, сохраняя внешние размеры.
4. Привести условные пустые состояния к стабильной карточке.
5. Проверить страницу с замедленными запросами, reduced motion, `npm run lint` и `npm run build`.

Откат не требует миграции данных: изменения ограничены React-разметкой и стилями, поэтому может выполняться возвратом соответствующих UI-изменений.

## Open Questions

Критичных открытых вопросов нет. Точное число строк-заглушек и значения `min-height` следует подобрать визуально во время реализации на фактической раскладке.
